# Slab v3.21.0 — Hopper Conditions

**One inbox. Many destinations. Zero clicks.**

Hopper learned a new trick. Until today every watched folder had exactly
one routing decision — run *this* recipe, save into *that* folder. Useful,
but most people don't have one kind of PDF; they have ten. Scanner output
mixed with downloaded invoices mixed with contracts the lawyer just
emailed. A single inbox couldn't sort them.

Now it can.

## Drop everything in one place. Slab sorts it.

Open Hopper, click **▸ Rules** on any watched folder, and write a chain
of routing rules. First match wins; non-matching files fall through to
the watch defaults. Six predicate kinds cover the cases people actually
need:

- **Filename glob** — `tax_*.pdf`, `*receipt*`, `Invoice-????-??.pdf`
- **Filename regex** — `(?i)(invoice|bill|statement)`
- **Text contains** — match on extracted content: `["invoice", "due date"]`
- **Page count between** — single-page PDFs are usually receipts; 5+ are reports
- **Size over** — scanned PDFs > 1 MB go through OCR; smaller ones don't
- **Always** — the catch-all fallback every chain should end with

Each rule then **overrides** any combination of recipe, output directory,
and rename pattern. Unset fields inherit from the watch — partial
overlays mean less to type.

## The live preview pane (a.k.a. the wow)

This is the part that costs an afternoon to build and saves users a day
of guessing. Open the rule editor and the right-hand pane shows up to
five real candidate files — the last four files the watcher actually
processed for this watch, plus a what-if filename you type. Each row
renders one chip per rule:

- **Green ✓** — the predicate matched this file
- **Solid green ring** — this is the winning rule (first match wins)
- **Grey ·** — predicate did not match

Every chip updates within ~150ms of any edit. You see "yes my tax PDFs
are caught by the `taxes` rule, and the catch-all isn't swallowing them"
*before* clicking Save. No more deploying a rule, dropping a test file,
and squinting at the run log.

The matching pipeline lives entirely server-side in Rust — the editor
just renders what `slab_hopper_test_rules` returns. So preview fidelity
is identical to production routing. Same code path, same answer.

## A real workflow

A paralegal's inbox might be:

```
1. tax_*.pdf            → flatten+OCR  → ~/Documents/Taxes/2026/
2. *receipt* / *.jpg.pdf → flatten     → ~/Documents/Receipts/
3. pages > 20            → bates+OCR   → ~/Documents/Legal/discovery/
4. text contains "lease" → bates       → ~/Documents/Legal/leases/
5. always                → (defaults)  → ~/Documents/Inbox/
```

Five rules, one inbox. Hazel can't see inside PDFs. Adobe AutoActions
require an enterprise license and ship your file to Adobe's cloud. Slab
does it free, locally, in 12 lines of UI.

## What's also new in v3.21.0

- **Run log gains a `matched_rule` column** — every Hopper run records
  which rule routed it (or `null` for default), so the audit trail tells
  you *why* a file ended up where it did.
- **TypeScript API parity** — `slabHopperGetRules`, `slabHopperSetRules`,
  `slabHopperTestRules` exposed in `$lib/hopper` for plugin authors who
  want to programmatically manage rules.
- **Onboarding step 6** introduces routing rules to existing users on
  next launch.

## Upgrading

In-place. Your existing watches keep their behaviour; rule chains start
empty. Add rules incrementally as you discover patterns in your inbox.

The sqlite migration (`ALTER TABLE watches ADD COLUMN rules_json`)
runs idempotently on first launch — no manual steps, no data loss,
fully backwards compatible with v3.20.0 databases.
