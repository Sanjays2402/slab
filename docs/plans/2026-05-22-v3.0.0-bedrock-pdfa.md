# v3.0.0 "Bedrock" — PDF/A Archival Conversion Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task. ~1500 net LOC + ~500 test LOC across 8 slices + release. ~9 commits.

**Goal:** Convert any PDF into a fully ISO 19005-compliant PDF/A-2b (and PDF/A-3b) archival document — embed fonts, embed sRGB v4 ICC profile, strip JavaScript/external refs/encryption, inject required XMP metadata, rewrite the document catalog with `OutputIntent`, and validate the result against ISO 19005-2 rules. Offline, free, cross-platform, one click.

**Architecture:** New `pdf::pdfa` Rust module owns the conversion pipeline as 6 ordered passes over a `lopdf::Document` (sanitize → font-embed → color-normalize → metadata-inject → output-intent → validate). Each pass is a pure function on `&mut Document` so they're independently testable. Frontend gets a `BedrockPanel.svelte` with conformance-level picker (2b/3b), pre-flight report (what's blocking), and a one-click Convert button. Reuses 100% of v0.8 font-subsetting infrastructure (already proven for OCR layer embedding); adds only ICC profile bundling + XMP packet writer + validator.

**Tech Stack:** lopdf 0.36 (workspace), `quick-xml 0.36` (XMP), `flate2 1.0` (already in tree), `chrono 0.4` (already), shipped sRGB IEC61966-2.1 ICC v4 profile (3.1 KB binary blob from `/System/Library/ColorSync/Profiles/sRGB Profile.icc` permissive-licensed redistribution → vendor under `assets/icc/sRGB_v4_ICC_preference.icc`). Zero new C deps. Pure Rust.

**Buy-Button audit (must pass before commit):**
- **Pay-for-it (YES)**: Adobe Acrobat Pro DC's PDF/A conversion is the #2 retention feature after Edit ($239/yr). PDFTron's library is $5k/seat/yr. Solid Documents PDF/A converter is $129. We ship it free.
- **Pick-us (YES)**: macOS Preview can't convert to PDF/A. PDF Expert can't. Free Foxit Reader can't (Pro is $159/yr and the conversion is buried). The only free cross-platform competitor is Ghostscript via CLI (`gs -dPDFA=2 ...`) which is unusable for non-engineers and routinely emits invalid output. Slab gives a one-click visual UI.
- **Notice-it (YES)**: new "Archive" sidebar entry between Compare and Slides, `Cmd+Shift+A` shortcut, command-palette entries, gold "PDF/A-2b ✓" badge on every successfully converted doc, settings section with default conformance level + outputs folder.
- **Tell-a-friend (YES)**: 8-second demo — drop a 50-page contract → click Convert → green "PDF/A-2b validated ✓" badge fades in with a gold seal-ripple anim → veraPDF (the ISO reference validator) opens it and says compliant. The fact that we then optionally pipe it through `verapdf` if installed for a third-party sanity check is buyer catnip.

**WOW (1/day quota):** Gold "rock-strata" reveal anim — 280ms cubic-bezier `(0.34, 1.56, 0.64, 1)` clip-path sweep from top with three horizontal gold strata lines (sandstone → granite → bedrock) that settle into the final compliant badge. Reduced-motion safe (fades in static badge instead).

**Pipeline position:** v2.4.0 Stack (just merged) → v2.5.0 Quill (forms, planned) → v2.6.0 Lens (OCR, planned) → v2.7.0 Signet (sign, planned) → v2.8.0 Forge (batch, planned) → v2.9.0 Vault (PKCS#11, planned) → **v3.0.0 Bedrock (THIS plan)**.

**Out of scope (explicitly deferred):**
- PDF/A-1 (legacy ISO 19005-1, requires CMYK or RGB *not both* and bans transparency — many real PDFs trip it). Targeting 2b is the modern sweet spot. v3.0.1 can add 1b.
- PDF/A-3 attachments inspector (we emit 3b only on user request; Slice 7 lets them ATTACH a sidecar but inspecting embedded attachments in someone else's PDF/A-3 is a separate v3.0.2 feature).
- PDF/UA accessibility tagging (v3.1.0 "Loom" — needs structure tree synthesis from text layout, big lift).
- Online VeraPDF validator integration (we ship offline-first; if user installs `verapdf` CLI we'll opportunistically run it, but cloud validators are out).

**Objective:** Document why 2b (not 1b or 3b default) is the right target.

**Files:**
- Create: `docs/adr/2026-05-22-pdfa-conformance-level.md`

**Step 1: Write the ADR**

```markdown
# ADR: PDF/A target conformance is 2b (default), 3b (opt-in)

## Status
Accepted, 2026-05-22.

## Context
ISO 19005 defines four families and three conformance levels per family:
- PDF/A-1 (2005, PDF 1.4): no transparency, no JBIG2, no embedded files,
  one colour family per document. Easiest to validate, hardest to *produce*
  from arbitrary input — most modern PDFs use transparency.
- PDF/A-2 (2011, PDF 1.7): allows transparency, JPEG2000, embedded PDF/A
  attachments, OpenType fonts. Sweet spot for real-world conversion.
- PDF/A-3 (2012, PDF 1.7): like 2 but allows arbitrary file attachments
  (XML invoices etc). Government / e-invoicing target.
- PDF/A-4 (2020, PDF 2.0): minimal differences for our use case; defer.

Conformance levels:
- a (accessible) — requires logical structure (PDF/UA). Out of scope.
- b (basic) — visual reproducibility only. Achievable from raster PDFs.
- u (unicode) — text Unicode-mappable. Achievable when fonts are embedded
  with ToUnicode maps (already true of every PDF that has selectable text
  in Slab today).

## Decision
- Default target: **PDF/A-2b**. Covers ≥95% of legal/contract/archival
  use cases users actually want.
- Opt-in via radio button: **PDF/A-3b** (when user wants to attach a
  sidecar XML/CSV).
- PDF/A-2u attempted opportunistically: if every font has a ToUnicode
  CMap we emit `<rdf:li>2U</rdf:li>` in the XMP. Validator will catch
  mismatches.

## Consequences
- One ICC profile to ship (sRGB v4) — covers RGB and grayscale via
  default greyscale colourspace.
- Transparency is allowed → no need to flatten (v2.0.3 Flatten remains
  a separate user choice).
- Embedded files are allowed in 2 and 3 (PDF/A-2 requires they be
  themselves PDF/A; we will warn but not reject in 2b, and validate
  attachments only in 3b mode).
```

```rust
//! Pass 1 of the PDF/A pipeline: remove forbidden interactive features.

use lopdf::{Document, Object};
use std::collections::HashSet;
use thiserror::Error;

#[derive(Debug, Error)]
pub enum SanitizeError {
    #[error("document is encrypted; decrypt before PDF/A conversion")]
    Encrypted,
    #[error("malformed document: {0}")]
    Malformed(String),
}

#[derive(Debug, Default, Clone)]
pub struct SanitizeReport {
    pub removed: Vec<String>,
}

/// Remove every entry ISO 19005-2 §6.6 forbids from the catalog and pages.
/// Returns a report listing what we removed (for the pre-flight UI).
pub fn sanitize_for_pdfa(doc: &mut Document) -> Result<SanitizeReport, SanitizeError> {
    if doc.trailer.get(b"Encrypt").is_ok() {
        return Err(SanitizeError::Encrypted);
    }

    let mut removed = Vec::new();
    const FORBIDDEN_CATALOG_KEYS: &[&[u8]] = &[
        b"OpenAction",  // forbidden if it's a JS action — we strip all to be safe
        b"AA",          // additional actions
        b"Names",       // may contain JavaScript dictionary
        b"AcroForm",    // form actions OK in 2b/3b but JS inside isn't; we sanitize sub-keys
    ];

    let catalog_id = match doc.trailer.get(b"Root") {
        Ok(Object::Reference(id)) => *id,
        _ => return Err(SanitizeError::Malformed("Root missing".into())),
    };

    let catalog = doc.get_object_mut(catalog_id)
        .map_err(|e| SanitizeError::Malformed(format!("catalog: {e}")))?
        .as_dict_mut()
        .map_err(|e| SanitizeError::Malformed(format!("catalog dict: {e}")))?;

    for key in FORBIDDEN_CATALOG_KEYS {
        if catalog.has(key) {
            // Special-case AcroForm: only strip its NeedAppearances + XFA
            if *key == b"AcroForm" {
                if let Ok(form) = catalog.get_mut(b"AcroForm").and_then(|o| o.as_dict_mut()) {
                    if form.has(b"XFA") {
                        form.remove(b"XFA");
                        removed.push("AcroForm.XFA".into());
                    }
                }
                continue;
            }
            catalog.remove(key);
            removed.push(String::from_utf8_lossy(key).into_owned());
        }
    }

    Ok(SanitizeReport { removed })
}
```

## Why this is the right next plan after Vault

The signature stack will be complete after Signet (v2.7) + Vault (v2.9). The next legal/enterprise lever isn't more signatures — it's **archival compliance**, the other half of why governments and law firms standardize on Adobe Pro. PDF/A is mandated by:

- US Federal Records Management (NARA Bulletin 2014-04)
- EU eIDAS Article 28 long-term preservation requirements
- ISO 14641 electronic archiving standard
- Most state court e-filing systems (NY, CA, TX all accept PDF/A-2b)
- IRS tax record retention guidance

Adobe charges $239/yr largely because nobody else ships a working PDF/A converter with a real UI. Ghostscript can do it via CLI but the output frequently fails veraPDF. Slab + Bedrock = the first free, offline, cross-platform, UI-driven, validated PDF/A converter. That's a buyer-magnet on par with Signet.

After v3.0.0 ships, the next plan in the queue would be **v3.0.1 PDF/A-1b fallback** for legacy-strict archives, then **v3.1.0 "Loom" PDF/UA accessibility tagging** (a/u conformance levels — the missing piece for ADA-compliance bulk processing in healthcare/edu).
