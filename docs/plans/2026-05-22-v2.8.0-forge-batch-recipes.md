# v2.8.0 "Forge" — Batch Recipes & Watch-Folder Automation

> **For Hermes:** Use the `subagent-driven-development` skill to implement this plan task-by-task. Fresh subagent per task, spec-compliance review then code-quality review, advance only on dual green. Order: v2.3.0 Theater → v2.4.0 Stack → v2.5.0 Quill → v2.6.0 Lens → v2.7.0 Signet → **v2.8.0 Forge**. If the queue moves, re-confirm this is still the highest-leverage next release before starting Slice 1.

**Goal:** Ship the single feature paralegals, legal-ops admins, and IT teams cite as the reason they bought Acrobat Pro: drag a folder of mixed-quality PDFs onto Slab, pick (or define) a **Recipe**, and walk away while Slab OCRs → auto-redacts PII → applies Bates numbers → flattens annotations → renames by detected date → drops a tidy production folder on the other side. Bonus: a **Watch-Folder** daemon does the same automatically when files land in a hot folder.

**Why this is the buy-button move.** Every Slab CLI op already exists in `src-tauri/src/pdf/`. The competitive moat isn't more ops — it's *composing* them so a non-engineer can run a 200-document discovery production from one drag-and-drop. Acrobat charges $24/seat/mo for "Actions" that do exactly this and require cloud upload. We ship it free, offline, with a designed UI.

**Architecture:**
- New crate-internal module `src-tauri/src/forge/` with three layers:
  1. **`recipe.rs`** — declarative `Recipe` struct (name, steps, settings), TOML serde, validation, schema versioning.
  2. **`runner.rs`** — `RecipeRunner` executes steps sequentially over a temp-dir pipeline; each step is one of ~16 `Step` enum variants that map 1:1 to existing `pdf::*` functions; emits structured progress events.
  3. **`watch.rs`** — `notify`-crate-backed file-system watcher per hot-folder; debounces, locks per-file to avoid double-processing, dispatches to runner.
- Recipes live in `~/Library/Application Support/com.slab.app/recipes/*.toml` (mac), `%APPDATA%/Slab/recipes/` (win), `~/.config/slab/recipes/` (linux). Three shipped examples: `legal-production.toml`, `redact-pii.toml`, `archive-ocr.toml`.
- Frontend: new `ForgePanel.svelte` with three tabs — **Run** (drop folder, pick recipe, see live progress), **Recipes** (list/edit/delete/duplicate, recipe editor with drag-to-reorder steps), **Watch** (manage hot folders, on/off toggle, last-run log).
- Command palette: `forge:run`, `forge:open-recipes`, `forge:add-watch-folder`. Shortcut: `Cmd+Shift+B` (B for "batch"; `B` alone is taken by Bates inside reader).
- A run is **atomic per file**: temp dir → all steps succeed → atomic rename to output. Any step error → file moves to `_failed/` subdir with `<name>.error.txt` next to it. Never overwrites the original.

**Tech Stack:** Rust 1.86 (existing `lopdf`, `regex`, `serde`, `toml`, `tokio`), `notify` crate (already a transitive dep — verify in Slice 1), Tauri v2 events, Svelte 5 runes, existing i18n (en/fr/es/ar).

**Buy-Button matrix:**
- Pay-for-it: ✅ a paralegal who runs 50 productions a year saves ~80 hrs/year vs. clicking through Acrobat one file at a time.
- Notice-it: ✅ new sidebar entry, new palette commands, new keyboard shortcut, recipe editor.
- Pick-us: ✅ Acrobat's "Action Wizard" requires Pro ($239/yr) + cloud upload for PII detection. Slab does it free + offline.
- Tell-a-friend: ✅ "drag folder, watch Slab do 200 PDFs in 3 minutes with a live progress UI" is a screenshot-bait demo.

**WOW moment:** the progress UI. Each file shows a horizontal pipeline of step chips (OCR → Redact → Bates → Flatten → Rename) that fill from grey to green left-to-right with a soft glow as each step completes, ETA recomputed live. Cancellable mid-run. Saved as a recipe-run history entry.

```rust
// src-tauri/src/forge/recipe.rs (add below Recipe)
use std::path::Path;
use crate::pdf::PdfError;

#[derive(Debug, Clone, Deserialize, Serialize, PartialEq, Eq)]
#[serde(tag = "op", rename_all = "snake_case")]
pub enum Step {
    Ocr { lang: String },
    AutoRedact { presets: Vec<String> },
    Bates { prefix: String, start: u32, width: u8 },
    Flatten { dpi: u32 },
    Compress,
    Encrypt { password: String },
    Watermark { text: String, opacity: f32 },
    Grayscale,
    Invert,
    Reverse,
    Sanitize,
    Nup { cols: u8, rows: u8 },
    Booklet,
    PageNumbers { start: u32 },
    RenameByDate, // step that reads first-page text, finds YYYY-MM-DD, renames file
    Merge,        // only valid as terminal step when input is a folder
}

impl Step {
    pub fn execute(&self, input: &Path, output: &Path) -> Result<(), PdfError> {
        use crate::pdf;
        match self {
            Step::Flatten { dpi } => {
                pdf::flatten::flatten(input, output, pdf::flatten::FlattenOpts { dpi: *dpi, ..Default::default() })?;
            }
            Step::Reverse => { pdf::reverse::reverse_pages(input, output)?; }
            Step::Grayscale => { pdf::grayscale::grayscale(input, output, Default::default())?; }
            Step::Invert => { pdf::invert::invert_colors(input, output, Default::default())?; }
            Step::Compress => { pdf::compress::compress(input, output)?; }
            Step::Encrypt { password } => { pdf::encrypt::encrypt(input, output, password)?; }
            Step::AutoRedact { presets } => {
                pdf::auto_redact::auto_redact(input, output, pdf::auto_redact::AutoRedactOpts {
                    patterns: vec![],
                    presets: presets.clone(),
                    gray: 0.0,
                })?;
            }
            Step::Sanitize => { pdf::sanitize::sanitize(input, output, Default::default())?; }
            // remaining variants forwarded to their respective pdf::* fns; fill
            // each one per the existing function signature. See header_footer.rs,
            // bates.rs, nup.rs, booklet.rs, page_numbers.rs, ocr.rs, watermark.rs.
            _ => return Err(PdfError::Other(format!("step {self:?} not yet wired"))),
        }
        Ok(())
    }
}
```

## Task 3: `RecipeRunner` with atomic per-file pipeline + progress events

**Objective:** A `RecipeRunner` that takes a folder + a `Recipe` and processes every PDF inside through every step, emitting structured progress, writing successes to `output_dir/` and failures to `output_dir/_failed/`. Atomic per-file: temp dir → rename on full success.

**Files:**
- Modify: `src-tauri/src/forge/runner.rs`
- Test: same file, inline tests

**API:**

```rust
pub struct RunRequest {
    pub recipe: Recipe,
    pub input_dir: PathBuf,
    pub output_dir: PathBuf,
}

#[derive(Debug, Clone, Serialize)]
pub struct RunProgress {
    pub file: String,
    pub step_index: usize,
    pub step_name: String,
    pub status: ProgressStatus, // Started | StepCompleted | FileCompleted | FileFailed { error }
    pub files_done: usize,
    pub files_total: usize,
}

pub struct RecipeRunner;

impl RecipeRunner {
    /// Process every *.pdf in input_dir through recipe.steps.
    /// Calls `on_progress` after each step + each file. Returns a summary.
    pub fn run(
        req: RunRequest,
        on_progress: impl Fn(RunProgress),
    ) -> Result<RunSummary, PdfError> { /* impl */ }
}

#[derive(Debug, Serialize)]
pub struct RunSummary {
    pub processed: usize,
    pub failed: usize,
    pub elapsed_ms: u128,
}
```

**Per-file algorithm:**
1. Create `tempdir`.
2. Set `cur = input_file`.
3. For each step `i` in `recipe.steps`:
   - `next = tempdir.join(format!("step{i}.pdf"))`
   - `step.execute(&cur, &next)?` (on err → bail, write `.error.txt`, copy original to `_failed/`)
   - emit `StepCompleted { step_index: i, ... }`
   - `cur = next`
4. Atomic rename `cur` → `output_dir/<original_name>`.
5. Emit `FileCompleted`.

**Tests:**
- `runs_two_files_through_two_step_recipe` — writes two tiny PDFs, runs Reverse + Grayscale, asserts both land in output_dir and 0 in _failed.
- `failed_file_goes_to_failed_dir` — pass a Recipe with `Step::Encrypt { password: "" }` (empty pwd → existing `encrypt()` returns Err) and confirm one file ends up in `_failed/`.
- `progress_callback_fires_in_order` — collect into a `Vec<RunProgress>` and assert ordering.

## Task 5: Watch-folder daemon

**Objective:** A `Watcher` that observes one or more hot folders and runs a recipe automatically on every new `.pdf` file landing inside, debounced to handle the editor-save flurry.

**Files:**
- Modify: `src-tauri/src/forge/watch.rs` (full content)

**Module shape:**

```rust
pub struct WatchConfig {
    pub hot_folder: PathBuf,
    pub output_dir: PathBuf,
    pub recipe: Recipe,
    pub delete_input_on_success: bool,
}

pub struct WatchManager { /* HashMap<PathBuf, JoinHandle<()>>, cancel tokens */ }

impl WatchManager {
    pub fn new() -> Self;
    pub fn start(&self, cfg: WatchConfig, window: Window) -> Result<WatchId, PdfError>;
    pub fn stop(&self, id: WatchId);
    pub fn list(&self) -> Vec<ActiveWatch>;
}
```

Implementation notes:
- One tokio task per hot folder. Uses `notify::RecommendedWatcher` in non-recursive mode.
- Debounce: after a `Create` or `Modify`, wait 750ms and re-check the file size is stable (two reads with the same size 250ms apart) before processing. PDFs are often written in two passes by scanners.
- Per-file lock: `HashSet<PathBuf>` of in-flight files; drop event if already processing.
- Forward `RunProgress` events to the window with watch_id stamped on.

**Tests:**
- `debounce_collapses_burst_writes` — write 5 events in rapid succession to a tempdir, assert the runner sees the file exactly once. Uses a stub runner.
