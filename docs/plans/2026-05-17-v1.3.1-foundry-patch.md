> **For Hermes:** Direct fixes on `feature/v1.3.1-foundry-patch`, no PR. Merge to main when green.

**Goal:** Unblock the v1.3.0 release by fixing the three cross-platform test failures CI surfaced on run 26011887503. macOS was green; Linux + Windows blew up. The product code is fine — the tests are platform-naive.

**Architecture:** Surgical. Three test fixes, zero behavior changes to shipping code (with one minor robustness tweak in `command_runner` to make the shell-timeout test pass in <3s on slow CI without relying on the kernel reaping a 10-second `sleep` process before our pipe reads finish).

## Failure inventory

From CI run `26011887503`:

### 1. Linux `cargo test` — `plugins::command_runner::tests::shell_timeout_kills_long_running`
```
panicked at src/plugins/command_runner.rs:297:9:
timeout should fire promptly, elapsed = 10.002203456s
```
Test expects elapsed < 3s. The wall-clock timeout DOES fire after 200ms (status is correctly `Timeout`), but then `read_to_string(child.stdout.take())` blocks for ~10s waiting for EOF. Why: `child.kill()` reaps `/bin/sh`, but `/bin/sh -c "sleep 10"` execs `sleep` as a child of the shell (or replaces the shell — depends on dash vs bash). On Linux runners (`/bin/sh` → dash), the `sleep` process inherits the stdout/stderr pipes from the shell. Killing the shell doesn't kill the sleep, and the pipes stay open until the sleep finishes.

**Fix:** Close the pipe handles BEFORE attempting to read on the timeout path. We're already not interested in any output that the killed process didn't write — and any partial data has already been flushed by the time we get here. By dropping the stdout/stderr pipe handles (instead of `read_to_string`-ing them) on the Timeout branch, we don't block on a stale grandchild.

### 2. Windows `cargo test` — `plugins::contributions::tests::read_asset_rejects_absolute_path`
```
panicked at src\plugins\contributions.rs:326:9:
assertion failed: err.contains("relative")
```
Test passes `"/etc/passwd"` and expects the absolute-path rejection branch. But on Windows, `Path::new("/etc/passwd").is_absolute()` is `false` (Windows considers paths absolute only if they have a drive letter or UNC prefix). So the path slides through the absolute-check and fails further down with "asset not found" instead.

**Fix:** Use a per-platform absolute path in the test (Unix: `/etc/passwd`, Windows: `C:\\Windows\\System32\\drivers\\etc\\hosts`).

### 3. Windows `cargo test` — `plugins::locale_loader::tests::rejects_absolute_path`
Same root cause as #2. Same fix.

## Task list (TDD-lite — failures are already known; verify per-platform after each fix)

### Task 1: Fix Linux `shell_timeout_kills_long_running` flake

**Objective:** Make the timeout path return in < 1s on Linux even when a grandchild process holds the stdout pipe open.

**Files:**
- Modify: `src-tauri/src/plugins/command_runner.rs` (the run_shell function, the Timeout branch)

**Step 1: Reproduce locally (sanity)**

Run: `cd src-tauri && cargo test --lib plugins::command_runner::tests::shell_timeout_kills_long_running -- --nocapture`

Expected on macOS (host): PASS (the test is flaky only on Linux dash; bash and macOS sh handle kill propagation differently). Document the platform-specific behavior in a comment.

**Step 2: Edit `command_runner.rs::run_shell`**

The current ordering:
```rust
let outcome = wait_with_timeout(&mut child, timeout);
if matches!(outcome, WaitOutcome::Timeout) {
    let _ = child.kill();
    let _ = child.wait();
}

let mut stdout_buf = String::new();
let mut stderr_buf = String::new();
if let Some(out) = child.stdout.take() {
    let _ = read_to_string(out, &mut stdout_buf);  // <-- BLOCKS on Linux dash
}
if let Some(err) = child.stderr.take() {
    let _ = read_to_string(err, &mut stderr_buf);
}
```

New ordering: skip pipe reads entirely on Timeout — we never report stdout/stderr to the user on timeout anyway (the stderr buf is overwritten with our `"(killed after Nms timeout)"` message in the match arm below).

```rust
let outcome = wait_with_timeout(&mut child, timeout);
let timed_out = matches!(outcome, WaitOutcome::Timeout);
if timed_out {
    let _ = child.kill();
    let _ = child.wait();
}

let mut stdout_buf = String::new();
let mut stderr_buf = String::new();
if !timed_out {
    if let Some(out) = child.stdout.take() {
        let _ = read_to_string(out, &mut stdout_buf);
    }
    if let Some(err) = child.stderr.take() {
        let _ = read_to_string(err, &mut stderr_buf);
    }
} else {
    // On timeout, deliberately drop the pipe handles WITHOUT reading.
    // /bin/sh on Linux (dash) doesn't propagate SIGTERM to its
    // exec'd children, so a grandchild like `sleep` keeps the
    // pipes open until it finishes on its own. Reading would
    // block the whole timeout path. The Timeout arm below
    // produces a synthetic stderr message anyway.
    drop(child.stdout.take());
    drop(child.stderr.take());
}
```

**Step 3: Verify the test passes**

Run: `cargo test --lib plugins::command_runner::tests::shell_timeout_kills_long_running`
Expected: PASS in <1s.

**Step 4: Verify no regressions in adjacent tests**

Run: `cargo test --lib plugins::command_runner`
Expected: all green.

**Step 5: Commit**

```
fix(plugins): don't block on stale pipes after shell-command timeout

CI failure on Linux: shell_timeout_kills_long_running took 10s
because /bin/sh -> dash doesn't propagate SIGTERM to exec'd
children. When we kill `sh`, its `sleep 10` grandchild keeps the
stdout/stderr pipes open, blocking our subsequent read_to_string
for the full sleep duration.

Fix: on the timeout path, drop the pipe handles instead of
reading them. The Timeout arm of the match produces its own
synthetic stderr message ("killed after Nms timeout") so we
weren't reporting the pipe contents to the user anyway.

Refs CI run 26011887503.
```
