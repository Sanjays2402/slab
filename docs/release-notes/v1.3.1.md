# v1.3.1 — Foundry Patch 🛠

> Cross-platform test fixes. No user-visible behavior changes. Releases
> what v1.3.0 should have shipped — CI on Linux + Windows was red on
> v1.3.0 due to three platform-naive tests, not real product bugs.

## What's in here

Three test fixes surfaced by GitHub Actions on tag `v1.3.0`
([run 26011887503](https://github.com/Sanjays2402/slab/actions/runs/26011887503)):

### 1. `plugins::command_runner::tests::shell_timeout_kills_long_running` (Linux)

Wall-clock timeout DID fire after 200ms — but the test then took 10s to
return because `/bin/sh` on Linux (Debian's `dash`) doesn't propagate
`SIGTERM` to its `exec`d children. Killing `sh` left a `sleep 10`
grandchild alive holding the stdout/stderr pipes open, and our
`read_to_string` blocked until that `sleep` exited on its own.

Fix: on the timeout path, drop the pipe handles instead of reading them.
The Timeout arm already produces a synthetic `"(killed after Nms
timeout)"` message — pipe contents were never reported to the caller on
timeout in any case.

Effect: shell-timeout regression test now returns in **~0.3s** (was
~10s on Linux runners; was already <1s on macOS).

### 2 & 3. `plugins::contributions::tests::read_asset_rejects_absolute_path` + `plugins::locale_loader::tests::rejects_absolute_path` (Windows)

Both tests passed `"/etc/passwd"` to exercise the absolute-path
rejection branch. But Windows's `Path::is_absolute()` returns `false`
for Unix-style paths — it expects a drive letter or UNC prefix. The
input slid past the absolute-check and got rejected with `"not found"`
instead of `"must be relative"`.

Fix: `#[cfg(unix)] / #[cfg(windows)]` to pick a hard-coded absolute path
the host platform's `Path` API recognizes (`C:\Windows\System32\drivers\etc\hosts`
on Windows).
