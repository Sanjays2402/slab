## Key design decisions

### Why preserve ocr_state on re-upsert
Scanner runs `scan_audit` on every changed file. If we always
overwrote `ocr_state`, a rescan after the queue produced an OCR'd
file would reset `ocr_done` → `scanned`, causing infinite re-OCR
loops. Solution: only upgrade from `unknown` to a real state;
never downgrade. The "real" terminal states (`ocr_done`,
`ocr_failed`) are sticky and only changed by the queue itself.

### Why `scan_audit` failure → `text_native`
Registry row must still land (the user has the file on disk). 
`text_native` is the safest fallback because it keeps the file
out of the OCR queue — no false positives that would burn CPU
on garbage input. A subsequent successful rescan can upgrade it.

### Why synchronous queue
Slice 2's goal was "user-visible end-to-end OCR pipeline." Async
worker + event stream would have been 2x the code for the same
UX (click button → wait → see status). The user already gets a
spinner via `ocringAll`/`ocringDocIds`. Async worker is now
deferred to Slice 7 of the roadmap, where it'll matter for
500-doc libraries.

### Why `ocr_output_path` stored in DB
UI needs to know where the searchable PDF lives without
re-deriving the naming convention. Also future-proofs if we ever
let users configure non-default output dirs (e.g. `~/Documents/
OCR-output/`).

### Why per-doc failures don't throw
`ocrQueueRunOne` returns `OcrQueueResult` with `error: string |
null` rather than throwing. This is so `ocrQueueRunAll` can
return one result per attempted doc; a single corrupt PDF or
missing Tesseract install shouldn't abort the whole batch.
